## 1. Кому и для чего нужен продукт

### Роли

**Участник:** студент или представитель работодателя. Заходит на страницу по QR-коду без аккаунта, видит актуальный вопрос, вводит 1–3 коротких слова/фразы, нажимает «Отправить» и получает подтверждение.

**Организатор:** Варвара Александровна и другие будущие организаторы. Заходит в защищённую панель, создаёт мероприятия/вопросы, управляет их активностью, переключает экран проектора, модерирует ответы, просматривает статистику и применяет рекомендации GigaChat.

**Зритель на проекторе:** видит один вопрос, live-облако и QR-код, либо два облака рядом, либо итоговое сравнение и краткие выводы.

### Сценарий 27 октября

Название демо-мероприятия: «Встреча студентов и работодателей — 27.10.2026». Два редактируемых вопроса:

1. Студенты: «Что вы ожидаете от будущей работы?»
2. Работодатели: «Какие навыки и качества вы ожидаете от будущих сотрудников?»

По словам организатора, работодателей ориентировочно **10 человек**. Это **не** предельное число пользователей и не ограничение на уровне системы. Ответы двух аудиторий должны храниться и отображаться раздельно, а при необходимости сравниваться. В будущем организатор создаёт новые мероприятия с любыми вопросами без изменения кода и повторного деплоя.

**Никакой принудительной привязки к словам «студенты/работодатели» для всех будущих мероприятий:** модель должна поддерживать определяемые организатором аудитории/группы или хотя бы универсальные роли/группы с настраиваемыми подписями. Для первого релиза достаточно ролей `student` / `employer` / `all` с редактируемыми названиями в интерфейсе.

## 2. Зафиксированный технический стек

- **Next.js (App Router), TypeScript, React, Tailwind CSS**. Брать совместимые стабильные версии, фиксировать через lockfile; не мигрировать на другой фреймворк без доказанной технической причины.
- **PostgreSQL** как источник истины, **Drizzle ORM** (либо Prisma при обоснованной причине). Миграции обязательны, таблицы и ограничения в БД; данные не должны жить лишь в RAM/контейнерных файлах или браузере.
- Серверный API в **Next.js Route Handlers**, входные данные проверяются **Zod**. Node.js runtime для GigaChat (не Edge runtime).
- Облако слов в локально поставляемом **SVG/Canvas** (например, `d3-cloud`); поддержка кириллицы, разные размеры по частотам, стабильная раскладка, разумный лимит слов на одном экране.
- QR-коды генерировать локально, без сторонних API.
- **Live-обновление через polling** каждые ~2 секунды с одним проектором и несколькими администраторами. Не делать WebSocket обязательным для MVP. `revision`/ETag, `Cache-Control: no-store`, пропуск перерисовки при неизменных данных, backoff на ошибках. Участникам не нужна постоянная двухсекундная синхронизация; раз в 5–10 секунд для смены активного вопроса достаточно.
- **Timeweb Cloud VPS в РФ** (Москва/Санкт-Петербург); резервный кандидат — **Selectel VPS в РФ**. Конфигурация-ориентир 2 vCPU / 4 ГБ RAM / 30–40 ГБ SSD; скорректировать по тестам, без самостоятельной оплаты.
- **Docker Compose + Nginx + HTTPS**; Next.js `output: 'standalone'`; PostgreSQL в приватной сети/volume. Linux Ubuntu LTS. Никакой необходимости в Vercel, Firebase, Supabase, Cloudflare, зарубежных CDN и сервисах идентификации.
- **GigaChat API (Сбер)** — обязательная интеграция первой версии, но необязательная для самой отправки ответов. Использовать бесплатный Freemium, **только если условия использования подходят для данного некоммерческого/учебного сценария и аккаунт реально имеет квоту**. В противном случае не обходить ограничения и сообщить заказчику, оставив ИИ-функции отключаемыми. Не подключать платный API автоматически.
- Часовой пояс интерфейса мероприятий: **Europe/Samara (UTC+4)**, хранение временных меток в UTC.

## 3. Обязательный пользовательский функционал

### 3.1. Панель организатора

- Вход по серверной аутентификации, выход, ограничение перебора пароля. Создание первого администратора безопасной командой/скриптом на сервере. Пароль не хранить в репозитории и не передавать в клиентском коде.
- Создать, отредактировать, дублировать, архивировать и открыть мероприятие; произвольное число вопросов, редактируемые группы ответивших, порядок вопросов.
- Настраивать вопрос: текст, целевая группа, количество ответов на участника (обычно 3), длина текста, статус `draft/open/paused/closed`.
- Управлять текущим вопросом для каждой группы, запускать/приостанавливать/завершать опрос. Открывать вопрос повторно, при этом сохранять уже собранные данные.
- Копировать постоянную ссылку для каждой аудитории и QR-код (PNG/SVG), выводить QR на проектор.
- Видеть принятые ответы и частоты; скрывать/возвращать слова, удалять демоданные, редактировать стоп-лист, работать с ручными алиасами.
- Получать предложения GigaChat об объединении синонимов и модерации, принимать/отклонять каждое или группу предложений.
- Получать краткое ИИ-резюме **по фактическим данным конкретного вопроса или мероприятия**, редактировать/удалять перед показом аудитории. Не включать автоматическую публикацию результатов ИИ без проверки человеком.
- Экспортировать сырые и агрегированные ответы в CSV UTF-8 BOM, разделитель `;` для Excel. Архив результатов сохраняется между мероприятиями.
- Иметь режим «Репетиция»: наполнить демонстрационными ответами с отдельной пометкой, очистить только демоданные одной подтверждаемой операцией.

### 3.2. Форма участника

- Постоянные адреса вида `/e/{slug}/{audience}`. Без регистрации, Telegram, установки приложения и внешних разрешений. Минимальное количество действий на телефоне.
- Название мероприятия, актуальный вопрос, поле ввода, кнопка, состояние отправки/успеха/ошибки, оставшийся лимит.
- Разрешать короткие слова и фразы («зарплата», «хороший коллектив»), адекватно обрабатывать кириллицу и ё/е.
- Ответ сохраняется атомарно в БД; повтор сетевого POST не создаёт дубликат. При недоступности API — сообщение об ошибке с возможностью повтора.
- Если вопрос не запущен / на паузе / завершён — внятный экран без возможности отправки.
- Анонимный случайный cookie-идентификатор участника + ограничение уникальных ответов **в БД**. Не применять глобальные запреты на IP как основную защиту, потому что участники могут пользоваться общим Wi-Fi/NAT.
- Для группы работодателей допускается включаемый администратором код доступа/приглашение; по умолчанию без усложнения. Убедиться, что QR ведёт именно к форме нужной группы.

### 3.3. Экран проектора

- Адрес `/e/{slug}/screen`, полноэкранный режим 16:9, читаемость на 1920×1080 в освещённом зале.
- Большой вопрос, QR и короткая ссылка, облако слов, число принятых ответов и число участников (с пометкой, что участники считаются приблизительно по анонимному ID).
- Чем чаще отправлен канонический ответ, тем больше слово. Цвета помогают различать; частота — не случайная и не AI-оценка.
- Отображение одного вопроса, двух групп рядом, переключение между ними; в будущем не ограничивать создание вопросов.
- Плавные обновления без F5 и без полной перестройки при неизменном `revision`; не перерисовывать облако на каждом polling-запросе.
- При кратковременном обрыве сети продолжать показывать последнюю корректную версию с ненавязчивым предупреждением.
- Пустое облако не считать ошибкой. Длинные слова/много слов/эмодзи/кириллица не должны ломать экран и перекрывать элементы.

### 3.4. Модерация и подсчёт

- Сохранять **исходный текст** каждого ответа неизменным. Для подсчёта создавать детерминированный канонический ключ: Unicode NFC, trim, унификация пробелов, нижний регистр, аккуратная нормализация `ё/е`, допустимая пунктуация.
- «ЗАРПЛАТА» и «зарплата» суммируются. «Высокая зарплата» не должна автоматически суммироваться с «зарплата», если нет подтверждённого правила/алиаса.
- В настройках вопроса редактируемые алиасы, стоп-лист, скрытые ответы, по необходимости предмодерация. На проектор отправлять только одобренные записи.
- Частоты и лимиты считаются транзакционно. Один и тот же участник не может накрутить одно слово многократным нажатием/перезапросом. Для одного вопроса можно иметь максимум несколько **разных** ответов на одного участника.
- Визуализация не исполняет HTML/JS. Лимиты длины/количества, rate limiting по участнику и разумное ограничение на IP как дополнительный сигнал, без блокировки общей сети.

## 4. GigaChat API: подробная спецификация (обязательная интеграция)

### 4.1. Назначение

**GigaChat — помощник организатора, а не источник статистики.** Основной механизм `ответ → БД → частота → облако` полностью детерминированный. ИИ вызывается **по нажатию в админке** или по отдельной фоновой задаче после накопления данных; не при каждом слове и не непосредственно из браузера участника.

Реализовать три действия:

1. **«Найти похожие ответы»**: по уникальным каноническим словам и их частотам GigaChat предлагает пары/группы выражений, близких по смыслу: «высокий доход», «хорошая зарплата» и т. п. В результате должны возвращаться `source[]`, `suggestedCanonical`, `reason`, `confidence` (оценка модели, не объективная вероятность). Только **предложение**; модератор утверждает или отклоняет. Изначальные ответы остаются в БД; применение правил пересчитывает частоты обратимым образом.
2. **«Помочь с модерацией»**: модель помечает потенциально неуместные, оскорбительные или не относящиеся к теме ответы с указанием причины. Не удалять автоматически по мнению ИИ; предлагать решение человеку. Серверный стоп-лист продолжает работать без ИИ.
3. **«Подвести итоги»**: дать организатору 3–5 коротких выводов на основе **реальных топ-слов, частот и количества ответов**, с осторожными формулировками. Для сравнения студентов и работодателей — пересечения и расхождения. Не домысливать мнения остальных людей; не подменять статистику. До одобрения человеком резюме не публикуется на проекторе.

Функции должны быть видимы и протестированы в админке **до 26 октября**, если подтверждены доступ и разрешённое использование бесплатного API. При отсутствии ключа или внешней ошибке пользователь видит «ИИ временно недоступен», а форма и облако продолжают работать. Не заменять GigaChat другим провайдером без согласования.

### 4.2. Официальный протокол и авторизация

Проверить актуальные документы и реализовать **server-to-server** доступ:

- Базовый адрес GigaChat: `https://api.giga.chat`, чат `POST /v1/chat/completions` (или документированный v2), использовать **модель из действующей бесплатной квоты**, первоначально `GigaChat-2` / `GigaChat` (Lite); конкретный ID подтвердить через `GET /v1/models` и тестовый запрос, не угадывать.
- Получить access token через `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth` с `Authorization: Basic <auth key>`, `RqUID: <uuid4>`, `Content-Type: application/x-www-form-urlencoded` и `scope=GIGACHAT_API_PERS` **для физлица**. Для юридического лица / иной лицензии scope выбирать строго по фактическому аккаунту.
- Access token действует **30 минут**. Делать безопасное обновление заранее, кэшировать только в памяти на сервере, обрабатывать 401 однократной принудительной переавторизацией, защищаться от stampede одновременного обновления.
- HTTPS/TLS: установить рекомендованные сертификаты НУЦ Минцифры в контейнер/на сервер и обеспечить нормальную проверку цепочки. **Запрещено** `NODE_TLS_REJECT_UNAUTHORIZED=0`, `rejectUnauthorized:false`, `curl -k` в production.
- Настройки только в серверных секретах: `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`, `GIGACHAT_MODEL`, `GIGACHAT_ENABLED`, `GIGACHAT_TIMEOUT_MS`, `GIGACHAT_MAX_INPUT_WORDS` и т. п. Ни один ключ, access token, полный auth header или приватные данные не должны уходить в клиентский бандл, GitHub, Actions logs и скриншоты.
- Если используешь официальный JS SDK, зафиксируй версию и подтверди, что он безопасно работает в Node runtime, с корректным `baseUrl` и SSL. Иначе реализуй небольшой типизированный REST-клиент. Никаких вызовов GigaChat напрямую с телефона посетителя.

### 4.3. Ограничения, безопасность и экономия квоты

- В Freemium для физлиц доступен **один одновременный поток генерации**. Реализовать **сериализацию GigaChat-заданий**: простую очередь/блокировку на сервере (для нескольких инстансов — блокировку через PostgreSQL), ограничение частоты запусков в админке, таймауты, retries с backoff только для безопасно повторяемых запросов. Не допускать лавины параллельных обращений.
- Обрабатывать `401`, `403`, `429`, `5xx`, нехватку квоты, timeouts, TLS-ошибки, отказы safety-фильтра. Текущий опрос никогда не блокируется из-за ответа модели.
- Передавать **пакеты уникальных слов с частотами**, а не сотни одинаковых сырых ответов. Обрезать пакеты согласно конфигу, не включать имена, телефоны, email, IP/cookie-ID и прочие персональные сведения. При необходимости удалять явно обнаруженные персональные данные перед передачей. Указать организатору, что слова/фразы отправляются в GigaChat для анализа.
- Опционально кешировать AI-результат по `(questionId, dataRevision, taskType, model)`; не обращаться повторно, если данные не менялись. Показывать время анализа, использованную модель и число проанализированных слов.
- Нельзя автоматически публиковать или применять семантические решения. Проверять JSON с Zod, валидация ссылок на **существующие** слова, запрет предложения объединить слово с выдуманной строкой. Ответы пользователей считать недоверенными инструкциями — игнорировать попытки prompt injection.
- Предпочесть официальную структурированную генерацию `response_format`/JSON Schema, если её поддерживает выбранная модель. Держать строгий schema validation и fallback на контролируемую ошибку.
- Фиксировать потребление токенов при наличии `usage`, админскую статистику расхода, не выводя ключи.
- Проверить лицензию и **ограничение Freemium на личное некоммерческое использование**. Участие компаний в колледжном событии само по себе не доказывает коммерческое использование, но и не означает автоматического разрешения: зафиксировать вывод с источником и при сомнении запросить решение владельца/правообладателя. **Никакого скрытого подключения платного пакета**. Для школьного/колледжного сервиса, принадлежащего организации, специально проверить соответствующий правовой режим.

### 4.4. Тесты GigaChat

- Mock-тест: предложения синонимов, проверка JSON, подтверждение/отклонение, повторный пересчёт частот, предотвращение утраты исходного ответа.
- Интеграционный smoke-test на реальном ключе **после предоставления секрета**: auth, test chat, schema response и отображение кнопок в админке; записать только статус/метрики, не секрет.
- Имитировать отсутствие ключа, лимит, timeout, 429, 5xx и некорректный JSON: опрос/проектор/экспорт должны продолжать работать.
- Убедиться, что единичный AI-вызов никак не задерживает POST-ответ участника.

## 5. Данные, транзакции и API

Схема PostgreSQL с миграциями и индексами минимум:

- `admins`, `admin_sessions`;
- `events`;
- `audiences` (настраиваемые группы);
- `questions`, `question_audiences`, `active_question`/состояния;
- `participants` (псевдонимный идентификатор в контексте мероприятия), `submissions`;
- `word_aliases`, `moderation_rules` / скрытые ответы, `event_settings`;
- `ai_jobs`, `ai_suggestions`, `ai_summaries` (с жизненным циклом queued/running/succeeded/failed и `dataRevision`).

В `submissions` хранить оригинальное слово, нормализованный ключ, роль/группу, вопрос, участника, статус, время, idempotency key. Уникальные ограничения и транзакции против повторной отправки и дублей одного канонического слова одним участником.

Спроектировать типизированные публичные endpoints для события, текущего вопроса роли, приёма ответа и облака (агрегаты + revision). Админ API: login/logout, CRUD, смена состояний, редактирование алиасов, модерация, экспорт, запуск и получение результатов AI jobs. Админская авторизация на каждом изменяющем маршруте, никакого «секретного» URL вместо авторизации. Списки сырых ответов никогда не отдавать анонимному проекторному/мобильному клиенту.

Сервер должен безопасно обрабатывать конкурирующие запросы; `Cache-Control: no-store` и отсутствие общего CDN кэша для live API. При необходимости хранить инкрементальный `revision` и снапшоты агрегата, но без преждевременной сложности.

## 6. Защита и доступность

- Только HTTPS, HSTS после проверки TLS. Админ-пароль хешировать Argon2id/scrypt, защищённые `HttpOnly Secure SameSite` cookies, серверные сессии, CSRF/Origin защита, ограничения на частоту логина. Не логировать секреты.
- Проверка допустимых состояний вопроса на сервере, валидация авторизации и ролей, защита от XSS/SQLi. Контроль доступа к экспорту, скрытым ответам и AI-вызовам.
- Не использовать IP как единственную меру защиты от накрутки; учитывать общий NAT, ограничивать по участнику, событию и умеренно по IP.
- При краткой потере интернета проектор держит последнее успешное состояние; повтор после ошибки передачи идемпотентен.
- Локально доставляемые CSS/JS/шрифты/иконки/QR: в браузере участника и на проекторе **нет обязательных запросов к зарубежным CDN, GigaChat API и внешним шрифтам**. GigaChat вызывается только российским сервером, и его сбой не влияет на базовый функционал.
- Отсутствие аккаунтов студентов, сбор минимальных данных. Не собирать ФИО, телефоны, геолокацию. Ясно указать анонимность (без обещания абсолютной невозможности идентификации).
- Backup PostgreSQL ежедневно и перед релизом, восстановление из backup протестировать. Ротация логов, healthcheck, автоподнятие контейнеров.

## 7. Инфраструктура: российский хостинг и запуск без VPN

- Основной вариант: российский VPS Timeweb Cloud с физическим размещением в РФ и публичным IPv4. Резервный: Selectel, российский регион. Только по согласованию стоимости с Вадимом.
- Docker Compose поднимает Next.js и PostgreSQL, Nginx принимает 80/443, выдаёт сертификат, проксирует API; PostgreSQL недоступна извне. Настроить volume, миграции, healthchecks, restart policies и firewall.
- Подготовить `Dockerfile` multi-stage, `compose.yaml`, конфиг Nginx, `.env.example`, `README.md`, `DEPLOY.md`, `BACKUP_RESTORE.md` и инструкции rollback. Не хранить настоящие секреты в Git.
- Убедиться, что Node-процесс достаёт `api.giga.chat` и OAuth endpoint с TLS-проверкой с сервера в РФ. Если исходящие вызовы временно не проходят, базовый продукт должен работать.
- DNS/HTTPS: использовать отдельный домен/субдомен или стабильный технический домен с корректным сертификатом. Не выдумывать URL и не считать успешным адрес, который существует лишь локально.
- Проверить открытие страницы, QR и отправку ответа на реальном iPhone/Android **без VPN из РФ** на нескольких независимых сетях (желательно один домашний Wi-Fi и два мобильных оператора). Если агент физически не может это проверить, предоставить короткий список точных проверок заказчику, отметить «не проверено», пока тест не проведён.
- Построение Docker-образов может зависеть от внешних реестров в процессе сборки; **во время мероприятия** приложение должно обслуживать формы/облако без любой зарубежной инфраструктуры. GitHub также не должен быть runtime-зависимостью production.
- Не оформлять платный VPS/домен самостоятельно; не просить заказчика делать системное администрирование. Агент настраивает все технические компоненты, когда необходимые права/оплата предоставлены.

## 10. Приоритеты при риске дедлайна

**P0 — без этого выпуск запрещён:** separate GitHub repo; Next.js/Postgres; готовые мероприятия/вопросы и роль организатора; анонимная мобильная отправка; облако с правильной частотой; QR/статусы; защищённая админка; реальная сохраняемость; российский HTTPS-сайт без VPN; базовые тесты/репетиция.

**P1 — включить в выпуск, если P0 стабилен:** модерация, сравнение, экспорт, архив, ручные алиасы, нагрузочные тесты, backups. Эти функции желательно иметь к 26 октября, потому что напрямую помогают мероприятию.

**AI-интеграция GigaChat — требование первой версии и отдельный гейт интеграции:** реализовать код, UI, моки и реальный smoke при наличии разрешённого доступа, **но** отсутствие ключа или временный сбой внешнего API никогда не должны задерживать P0 и срывать встречу. Если доступ/условия использования заблокированы, зафиксировать это как отдельный неготовый AI-пункт; не выдавать полностью реализованный GigaChat за подключённый.

**P2 — после мероприятия:** темы брендинга, облака в виде конкретных фигур, PDF-отчёты, расширенная аналитика, мультиорганизации, автоматические умные правила, полноценные WebSockets, сторонние интеграции.

## 11. Тесты и количественные критерии приёмки

Проверить через CI и на реальном окружении:

- `lint`, `typecheck`, unit, integration API+PostgreSQL, Next.js build, Playwright E2E;
- нормализация русских слов, повторная отправка, конкурентные POST, 3-ответный лимит, смена вопроса, разделение ролей, повторное открытие вопроса;
- после модерации и ручного алиаса облако отражает правильные частоты, а исходные ответы неизменны;
- AI тесты: токен/обновление, очередь одного потока, JSON schema, модераторское подтверждение, отключение/429/timeout;
- не менее 200–300 конкурентных участников в воспроизводимом нагрузочном тесте; 1–2 экрана просмотра, измерение реального p95 и процента ошибок;
- при нормальном интернете ответ виден на проекторе за **3–5 секунд** (цель, подтверждается замером);
- без VPN в РФ открываются frontend, POST API, admin login и экран проектора; внешний GigaChat не требуется для запуска;
- restart контейнера и восстановление PostgreSQL не теряют ответы; тестовая очистка не удаляет реальные данные;
- нет секретов в Git/логах и P0 security уязвимостей; НУЦ Минцифры используется с проверкой сертификата;
- финальная репетиция: два разных QR, минимум несколько телефонов, 10 демонстрационных ответов работодателей, разные слова/синонимы/регистр, проектор 16:9, pause/resume, смена вопросов, экспорт и AI-помощь, если активна.

Никогда не заявляй «тесты пройдены», если не запускал соответствующие команды. В отчёте указывай дату, окружение, команду, вывод и ссылку на Actions/скриншот. Для теста без VPN — название проверенной сети/оператора; при отсутствии проверки честно ставь `не проверено`.
